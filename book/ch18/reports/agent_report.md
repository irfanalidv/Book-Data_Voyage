# Chapter 18 — Agent Report

_Generated by `ch18_agentic_ai.py`. The agent runs five test
queries (see `book/ch18/data/query_viability.txt` for what's
answerable on the bundled data). For each query the report
captures tool-call count, latency, token usage, cost estimate,
and the agent's final response. Full traces are in
`book/ch18/reports/traces/`._

## Conventions

- **Tool-call count** is the number of times the agent invoked
  any tool function in one run. Includes failed tool calls.
- **LLM calls** is the number of round trips to the model. Always
  ≥ tool-call count + 1 (the model decides what to call between
  tool returns).
- **Latency** is wall-clock from `Agent.run()` entry to return.
  Dominated by LLM round trips on Groq's free tier.
- **Cost** is estimated from token counts × Groq's published
  pricing for the model used. Approximate; real billing may
  vary slightly.
- **Cached vs live**: by default the chapter executable reads
  cached responses from `book/ch18/reports/traces/cache/`. The
  committed report is regenerated with `--live` so the numbers
  represent fresh API calls. Cached reruns are free; live runs
  cost approximately the per-query cost shown.

## Failure-mode catalogue

Failures observed across the five test queries, with citations
to specific trace files. Each entry describes what was observed,
what caused it, and how the loop responded. **Five numbered
failure-mode categories** follow (a single trace can illustrate
more than one).

### 1. Llama tool-format quirk (Groq 400 tool_use_failed)

**Observed in:** `compare_top_three.json`, `ambiguous.json`

**What happened:** The LLM (Llama 3.3 70B via Groq) emitted a
tool call in XML-style markup instead of the OpenAI-compatible
structured format Groq's API expects. Example raw output:

```
<function=search_jobs {"query": "AI Engineer", "k": 3}</function>
```

The model correctly identified the tool name and the argument
values; it just serialised them as XML tags rather than as a
structured `tool_calls` field. Groq's API receives this and
returns a 400 with `code: tool_use_failed` and the malformed
string in `failed_generation`.

**Why it happens:** Llama family models were trained with
multiple tool-calling formats during fine-tuning, including
xml-style. Under temperature 0.0 the model is deterministic
but not consistent across prompts — some inputs trigger the
structured format, others trigger the XML form. The malformed
cases tend to cluster around ambiguous queries ("show me good
jobs") and terminology-mismatched queries ("AI Engineer" when
the data has no such role_category), where the model is less
confident about which tool to call.

**How the loop responded:** The agent caught the BadRequestError,
captured the full response body, set `stop_reason="error"`, and
returned with no tool calls executed. The chapter's measurement
contract is preserved — every query produces a trace, including
the failed ones.

**Mitigations (deferred, see ROADMAP.md):**
- Retry once with a clarified system prompt instructing the
  model to use structured tool calls.
- Fall back to text-only response with a "no good answer"
  message when tool calls fail.
- Switch to a model with more reliable tool-calling (GPT-4 or
  Claude — also deferred).

### 2. Agent chains tools but produces wasted calls before recovering

**Observed in:** `ml_engineer_classify_chain.json`

**What happened:** Given "Find ML Engineer postings, then classify
each to confirm the actual role matches the title," the agent
issued 11 tool calls across 3 LLM rounds. The first call was a
correct `search_jobs("ML Engineer")` returning 5 real postings
with real job_ids (demo_42_0004 through demo_42_0042). The
second through sixth calls were `classify_role` invocations
using placeholder argument values — literally the string
`"job_id_from_search_results_1"` instead of the actual job_id
`demo_42_0004` from the search response. All five returned
`{"error": "not_found"}`.

The LLM then read the structured error envelopes, realised it
needed the real `job_id` field from the search results, and
re-issued `classify_role` calls with the correct IDs (calls 7-11).
Those succeeded. The final response — "All the job postings
have a predicted role of ML Engineer with a confidence score
of 0.73" — is correct.

**Why it matters:** The user-facing response is correct. The
agent self-corrected. But it spent 5 of 11 tool calls on a
confused argument-passing pattern that produced no useful
output. On Groq's free tier this is invisible to the user; in
production with a more expensive provider or against tools
that mutate state, this would have been a real problem.

The chapter's lesson here is one most agent tutorials skip:
**a correct final response can sit on top of multiple wasted
tool calls.** When evaluating an agent, looking only at the
final response misses where the cost (latency, dollar, error
surface) actually accrues. Trace inspection is not optional.

**Recovery mechanism:** The agent recovered because
`get_job_detail` and `classify_role` return structured error
envelopes (`{"error": "not_found", "job_id": ...}`) instead of
raising. The LLM read the structured errors and adjusted. If
the tools had raised exceptions or returned generic error
strings, the loop would have either crashed (raise) or
stalled in a confused state (generic strings). Structured
error envelopes are a load-bearing design choice for agent-
consumed tools.

### 3. Honest "no results" reporting when search returns empty

**Observed in:** `no_good_answer.json`

**What happened:** Given "Find postings for Quantum Engineer
roles" — for which the bundled corpus has zero matching rows —
the agent called `search_jobs("Quantum Engineer")` once, received
an empty list, and reported back honestly in plain text that no
matching postings exist. No hallucination. No invented job_ids.

This is evidence that system-prompt rule 5 ("If a search returns
no results, tell the user honestly — do not invent results")
does real work. Without that rule, the LLM's natural completion
behaviour would likely have been to fabricate a plausible-
sounding Quantum Engineer posting. The lesson: a one-line
system-prompt rule was load-bearing for the agent's honesty.

### 4. Rate-limit retries add latency variance, not cost

**Observed in:** All natural-completion queries (variable
severity across runs).

**What happened:** Groq's free tier rate-limits to roughly 30
requests per minute for the Llama 3.3 70B endpoint. Multi-step
queries can saturate this and trigger 429 responses, which
the groq Python client transparently retries with backoff
(typically 3-11 seconds per retry). Across two consecutive
live runs, `ml_engineer_classify_chain` took 24.3s and 6.4s —
the same agent behaviour, with retry latency dominating in the
first case.

Cost per query is unaffected by retries (retried calls don't
bill twice). Wall-clock latency is. Production deployments
that need predictable latency should either move to a paid tier
with higher rate limits or implement their own queueing layer.

This is named in the report's preamble; the chapter's prose
will discuss it as the gap between "cost is predictable" and
"latency is predictable" — two things readers often conflate
when budgeting agent infrastructure.

### 5. LLM confuses argument references with literal strings

**Observed in:** `ml_engineer_classify_chain.json` (calls 2-6)

**What happened:** The agent was told to chain `search_jobs`
→ `classify_role`. The LLM correctly understood the workflow
but mishandled argument passing — it produced 5 tool calls
with `job_id` set to the literal string
`"job_id_from_search_results_1"` (through `_5`) rather than
extracting the actual `job_id` field from the search response.

**Why it happens:** Tool-calling LLMs do not have execution-
time variable bindings. The model reads the previous tool's
output as text in the message history, and constructs the
next call by generating tokens. When the prompt or the
previous output uses placeholder-like phrasing
("the job_id from search result 1"), the model can copy that
phrasing into the argument value rather than resolving it to
the actual ID. The fix is in how tools structure their
responses — labelled fields with clear types — not in how
the agent is prompted.

**How the loop responded:** No code change; the tools returned
`{"error": "not_found"}` for each placeholder, the LLM read
these in the next round, and the next round's tool calls used
the correct IDs. The agent self-corrected at the cost of 5
wasted tool calls (~0.84s total tool-execution time, plus 1
additional LLM round).

**Mitigations:**
- **Already in place:** Structured error envelopes from tools
  (returning a dict with an "error" key, not raising). This
  gives the LLM something concrete to read and recover from.
- **Deferred (see ROADMAP.md):** Inserting explicit "use the
  `job_id` field from the previous response" instructions in the
  system prompt. This would likely reduce the wasted-call rate
  but couples the prompt to specific tool schemas.
- **Deferred:** Switching to a tool-calling provider with more
  reliable argument extraction (OpenAI's function calling has
  historically been more reliable here; Anthropic's tool use
  similarly).

## Bundled-data limitations

The traces were recorded in May 2026 against an earlier version of
the bundled corpus: 540 heavily templated demo rows in which
`role_category` held only Data Scientist, ML Engineer, and Data
Engineer. Job IDs in the traces (`demo_42_…`) come from that
version and do not exist in the current bundled file.

- Queries for AI Engineer could not return role-matched results;
  the agent fell back to the closest role.
- Descriptions were near-identical, so `summarise_for_candidate`
  produced similar summaries for similar postings.
- None of the five failure modes depends on those limitations —
  they are properties of the agent loop and the model. Replay mode
  reproduces the recorded run exactly; `--live` records a new one
  against the current corpus.
