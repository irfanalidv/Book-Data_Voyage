## Why this practice, and why now

Chapter 1 answered *what field am I entering?* Chapter 2 answers *how do working engineers structure the code that field runs on?*

We teach this immediately after the environment check because every chapter from here assumes the same imports:

```python
from talentlens import get_settings, REPO_ROOT, DATA_DIR
```

If we waited until Chapter 5 (data collection), you would have already written three chapter scripts with duplicated path logic and three different conventions for reading API keys.

**What we are not doing:**

- **`setup.py` as the packaging entry point**: deprecated in favour of [`pyproject.toml`](https://github.com/irfanalidv/Book-Data_Voyage/blob/main/pyproject.toml) (PEP 621). New projects should not add `setup.py` unless they are maintaining legacy packaging.
- **Raw `os.environ.get()` for configuration**: no validation, no types, secrets scattered through call sites. We use pydantic-settings (see below).
- **`print()` for diagnostics**: fine for a one-off script; useless when you need log levels, filtering, or production log aggregation.
- **Teaching Python syntax**: you already know loops and comprehensions. This chapter is practice, not language basics.

**What Chapter 22 will do with today's work:** the `talentlens/` package you create here is the *development* copy inside the monorepo. In Chapter 22 we extract `talentlens_core` to PyPI as `talentlens-core`, the installable library consumers `pip install` without cloning the book. Same modules, different packaging boundary. Building the dev package correctly now means the extraction is a move, not a rewrite.

## The methods

> **Skip ahead if…** you already run pyproject-based projects with a Makefile and pydantic-settings. Skim to the TalentLens-specific decisions ([`talentlens/paths.py`](https://github.com/irfanalidv/Book-Data_Voyage/blob/main/talentlens/paths.py), `get_settings()`, and the checkpoint at the end).

### `pyproject.toml`: the project contract

[`pyproject.toml`](https://github.com/irfanalidv/Book-Data_Voyage/blob/main/pyproject.toml) is the single file that tells tooling who you are and how to build you.

> **Reference: pyproject.toml sections**

| Section | Purpose |
|---------|---------|
| `[build-system]` | Which backend builds the package (`setuptools` here). |
| `[project]` | Name, version, authors, `requires-python`, runtime `dependencies`. |
| `[project.optional-dependencies]` | Feature groups (`dev`, `ml`, `llm`) so readers install heavy stacks only when needed. |
| `[tool.ruff]` | Linter + formatter config: one tool instead of flake8 + isort + autopep8. |
| `[tool.mypy]` | Static types; strict on `talentlens/`, relaxed on `book/ch*/` teaching scripts. |
| `[tool.pytest.ini_options]` | Where tests live (`tests/` at repo root for chapter integration tests). |

**Why not only [`requirements.txt`](https://github.com/irfanalidv/Book-Data_Voyage/blob/main/requirements.txt)?** [`requirements.txt`](https://github.com/irfanalidv/Book-Data_Voyage/blob/main/requirements.txt) pins versions for reproducible installs. [`pyproject.toml`](https://github.com/irfanalidv/Book-Data_Voyage/blob/main/pyproject.toml) makes the tree *installable* with `pip install -e .` so `import talentlens` resolves from anywhere in the repo. You need both: pins in requirements for the full book stack, metadata in pyproject for the package boundary.

### Virtual environments: pick one default

> **Reference: Virtual environment tools**

| Tool | When it wins | Why we do not default to it here |
|------|----------------|-----------------------------------|
| `python -m venv .venv` | Standard library, no extra install | **Our default**; matches CI and most teams |
| Poetry | Lockfiles + publish workflow in one CLI | Extra abstraction; book already pins in [`requirements.txt`](https://github.com/irfanalidv/Book-Data_Voyage/blob/main/requirements.txt) |
| pipenv | Pipfile lock | Less common in ML repos in 2026 |
| Conda | Scientific stack with binary deps | Heavy; use when CUDA/system libs require it |

**Recommendation:** `python -m venv .venv`, activate, `make install`. Chapter 1 already walked you through this.

### Type hints and ruff

Type hints are documentation the interpreter can check. We type every public function in `talentlens/` and chapter entrypoints. Ruff enforces import order, unused imports, and many bug classes flake8 used to catch, without a second formatter pass for imports.

Run quality checks the way CI will:

```bash
make lint          # same checks as CI (ruff E,F,W,I + black on book/, tests/, talentlens/)
make lint-all      # full pyproject ruff rules — stricter, optional locally
ruff format book/ch02/ talentlens/   # direct formatter when you want ruff only
```

The repo's `make format` target invokes black, because CI checks formatting with black. `ruff format` produces near-identical output; use whichever your team standardises on, and make CI check the same one.

### Configuration: pydantic-settings vs `os.environ`

**The brittle pattern** (do not ship this):

```python
import os

LOG_LEVEL = os.environ.get("LOG_LEVEL", "INFO")
DATA_DIR = os.environ.get("DATA_DIR", "./data")
OPENAI_API_KEY = os.environ.get("OPENAI_API_KEY")  # None or str — no validation

if LOG_LEVEL not in ("DEBUG", "INFO", "WARNING", "ERROR"):
    raise ValueError("bad log level")  # you write this by hand, every project
```

Problems: defaults are strings until you coerce them; paths stay strings; invalid `LOG_LEVEL` fails at runtime in random places; optional secrets are indistinguishable from empty strings; nothing documents which variables exist.

**The pattern we use** (pydantic v2 + pydantic-settings):

```python
from functools import lru_cache
from pathlib import Path

from pydantic import SecretStr
from pydantic_settings import BaseSettings, SettingsConfigDict

from talentlens.paths import REPO_ROOT


class Settings(BaseSettings):
    model_config = SettingsConfigDict(
        env_file=".env",
        env_file_encoding="utf-8",
        extra="ignore",
    )

    log_level: str = "INFO"
    data_dir: Path = REPO_ROOT / "data"
    openai_api_key: SecretStr | None = None
    groq_api_key: SecretStr | None = None


@lru_cache
def get_settings() -> Settings:
    return Settings()
```

Wins: `data_dir` is a `Path`; missing `.env` is fine; wrong types fail at startup with a clear pydantic error; `SecretStr` keeps keys out of accidental logs; `get_settings()` is cached so you do not re-parse the environment on every import.

**Import rule for 2026:** use `from pydantic_settings import BaseSettings`, not `from pydantic import BaseSettings` (removed in Pydantic v2). The book pins `pydantic==2.13.3`.

### Logging: `logging.getLogger(__name__)` vs `print()`

```python
import logging

logger = logging.getLogger(__name__)

logger.debug("Only when LOG_LEVEL=DEBUG")
logger.info("Normal diagnostic — filterable in production")
```

`print()` always goes to stdout with no level. Logging lets you turn verbosity up for debugging and down for demos without editing code. Chapter 2's script uses logging for diagnostics and a short `print()` banner for the final "ready" message, the same pattern as Chapter 1's environment check.

### `Makefile` as the command interface

Every repeated command becomes `make <verb>`:

> **Reference: Makefile targets**

| Target | What it does |
|--------|----------------|
| `make install` | `pip install -r requirements-lock.txt`, then `pip install -e .`, then the spaCy model |
| `make install-dev` | Runtime install plus lint and test tools (ruff, black, pytest) |
| `make test-ch01` | Chapter 1 tests (environment check) |
| `make test-ch02` | Chapter 2 tests (config + paths) |
| `make test` | Full suite under `tests/` |
| `make lint` | ruff check (the same rules CI enforces) plus a black formatting check |
| `make clean` | Remove generated artefacts |

When Priya joins, she does not need your shell history. She runs `make help`.

### `pre-commit` hooks

`.pre-commit-config.yaml` runs ruff and file hygiene checks before each commit. Hooks catch trailing whitespace and accidental large files; they do not replace `make test`. Install once:

```bash
pip install pre-commit
pre-commit install
```

## The code

Runnable entrypoint:

```bash
python book/ch02/ch02_python_setup.py
```

**Design decision 1: import from `talentlens`, not from a relative path.** The script starts with `from talentlens import get_settings, REPO_ROOT`. That only works after `pip install -e .`, which is intentional: if you skip the install step, you find out before Chapter 5's collector fails mysteriously.

**Design decision 2: `get_settings()` is cached.** `functools.lru_cache` on the factory means environment parsing happens once per process. Chapter 19's FastAPI app will call the same function inside dependencies.

**Design decision 3: secrets masked in output.** `Settings.mask_secrets()` redacts API keys before printing. Never log raw `SecretStr` values.

If you have filled in `.env`, the two key lines read `***set***` instead of `None`; the value itself never prints.

**Verify the install:**

```bash
python -c "import talentlens; print(talentlens.__file__)"
```

You should see a path inside this repository (`.../Book-Data_Voyage/talentlens/__init__.py`). That is what an editable install means: Python imports the package from your working tree, so edits take effect without reinstalling.

**`make help`**: lists every target with a one-line description. If `test-ch02` is missing, the Makefile patch from this chapter did not land.

## Common mistakes I've seen (and made)

**Mistake: Hardcoded paths that work on the author's laptop**

What happens: `pd.read_csv("/Users/irfan/Book-Data_Voyage/data/jobs.csv")` runs in your notebook. A reader clones on Linux, paths break, they blame pandas.

How to catch it: grep for `/Users/` or `C:\\` in the repo. Replace with `DATA_DIR / "jobs.csv"`.

---

**Mistake: [`requirements.txt`](https://github.com/irfanalidv/Book-Data_Voyage/blob/main/requirements.txt) without [`pyproject.toml`](https://github.com/irfanalidv/Book-Data_Voyage/blob/main/pyproject.toml)**

What happens: teammates `pip install -r requirements.txt` and can run scripts, but `import talentlens` fails because nothing declares a package. Six months later nobody can publish or test the tree as a unit.

How to catch it: fresh venv, only `pip install -r requirements.txt`, try `import talentlens`. If it fails, add `pip install -e .` to your onboarding docs (we add it to `make install` here).

---

**Mistake: `print()` instead of `logging.getLogger(__name__)`**

What happens: debugging an ingestion pipeline at 2 AM, you add twenty `print()` calls. In production there is no way to silence them or route errors to your log aggregator.

How to catch it: code review for `print(` in library modules under `talentlens/`. Prints in `if __name__ == "__main__"` banners are fine.

---

**Mistake: Secrets committed because `.env` was not in `.gitignore`**

What happens: `GROQ_API_KEY=gsk_...` lands in git history. You rotate the key and still get security scanner emails forever.

How to catch it: only `.env.example` belongs in git; real `.env` stays local. pre-commit's large-file hook catches some accidents, not all.

---

**Mistake: Everyone runs different commands**

What happens: you run `pytest tests/`, Priya runs `python -m pytest book/ch02/tests`, CI runs `make test-ch09` only. Failures reproduce on one machine.

How to catch it: if a task appears twice in README, Makefile, and a GitHub workflow, pick one canonical entry (Makefile) and link to it.

## Interview questions

**Q1: What belongs in a good [`pyproject.toml`](https://github.com/irfanalidv/Book-Data_Voyage/blob/main/pyproject.toml) for a data/ML project?**

Template answer: "At minimum: `[build-system]`, `[project]` with name, version, `requires-python`, and dependencies, plus tool sections for the linter and test runner. Optional dependency groups keep heavy ML stacks out of the default install. The file should make `pip install -e .` work so internal packages import cleanly. Version pins for reproducibility often stay in [`requirements.txt`](https://github.com/irfanalidv/Book-Data_Voyage/blob/main/requirements.txt) or a lockfile; pyproject declares what the package *is*, not every transitive pin."

**Q2: Why pydantic Settings instead of `os.environ.get()`?**

Template answer: "Environment variables are untyped strings. Settings classes coerce types, validate values at startup, document allowed fields, and support `.env` files through `SettingsConfigDict`. Secrets can use `SecretStr` so they do not leak into logs. A cached `get_settings()` factory gives one validated instance per process, the same pattern FastAPI dependency injection uses later."

**Q3: How do you structure a Python project for production?**

Template answer: "Separate installable library code from entrypoints and notebooks. Root [`pyproject.toml`](https://github.com/irfanalidv/Book-Data_Voyage/blob/main/pyproject.toml), src or top-level package (`talentlens/`), `tests/` mirroring modules, config via settings not globals, logging module per package, Makefile or task runner for repeatable commands, pre-commit for style, CI running the same targets. Data lives outside the package under `data/` with paths resolved from repo root."

**Q4: What does ruff replace and why use it?**

Template answer: "Ruff replaces flake8, isort, pyupgrade, and much of the autopep8/black workflow for linting and formatting in one fast binary. Fewer tools means fewer version conflicts in CI. We still pin versions in pre-commit so local and CI match."

**Q5: How do you handle config across dev, staging, and prod?**

Template answer: "Same settings class, different `.env` files or environment variables injected by the host. Never branch on `if os.getenv('ENV') == 'prod'` scattered through code. One Settings object, different values. Secrets from the environment or secret manager, never committed. Defaults safe for local dev (e.g. `LOG_LEVEL=INFO`, data dir under repo root)."
